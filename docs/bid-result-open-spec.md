# 입찰 결과 — g2bmastersopen 기능 명세

이 문서는 **g2bmastersopen**(이하 *open*)의 "입찰 결과" 탭이 실제로 제공하는 기능을
코드에서 확인해 정리한 것이다. 이 저장소(g2bmaster-frontend)가 같은 화면을 React 로
옮길 때의 기준선으로 쓴다.

- 기준 커밋: `Electerior/g2bmastersopen` `origin/main` (`1a4cad7`)
- 확인 방법: 커밋된 트리만 읽었다(`git show 'origin/main:<path>'`). 워킹트리의 미커밋
  변경은 반영하지 않았다.
- `origin/fix/redirect-to-primary-domain` 의 `server.js`·`public/app.js` 는 `origin/main` 과
  blob sha 가 같다. 즉 그 브랜치는 코드가 아니라 배포 설정만 바꿨으므로 여기서는 main 과
  같이 다룬다.
- open 의 `dev`·`fetch` 브랜치는 입찰 결과 **탭 자체**는 main 과 사실상 동일하다.
  `TABS['bid-result']` 블록과 이 탭을 떠받치는 라우트 4개는 세 브랜치가 같다.
  갈리는 지점은 이 문서 마지막 절에 따로 적었다.

---

## 1. 이 탭이 무엇인가

나라장터 **낙찰정보서비스**(`ScsbidInfoService`)를 실시간으로 조회하는 화면이다.
동시에 개찰 참여업체·들러리 담합·낙찰자 이력으로 내려가는 **사후 경쟁정보의 진입점**이다.

한 가지 성격을 먼저 못 박아 둔다: 이 탭은 **DB 를 경유하지 않는다.** open 은 요청마다
조달청 API 를 직접 치고 메모리에 캐싱할 뿐이다(`server.js:1581-1657`). 낙찰 데이터를
적재해 두고 읽는 구조가 아니다.

---

## 2. 진입 경로

| 경로 | 동작 |
|---|---|
| 탭 클릭 | `state.tab='bid-result'`, 페이지 1, 정렬을 개찰일시(`rlOpengDt`) 내림차순으로 리셋 후 `GET /api/bid-result` |
| 입찰 공고 행의 `낙찰결과 →` | 입찰 결과 탭으로 이동하며 **그 공고의 공고명 전체를 AND 키워드 하나로** 넣어 재검색 (`public/app.js:2045`) |
| 검색 모드를 `낙찰자 조회`로 변경 | 현재 탭이 무엇이든 입찰 결과 탭이 강제 활성화된다 (`public/app.js:1056-1059`) |

`마감 전 공고만 보기` 체크박스는 이 탭에서 강제로 숨겨진다. 낙찰 결과에 마감 개념이 없다.

## 3. 검색 · 조회

### 3.1 조회 파라미터

`GET /api/bid-result` 가 실제로 읽는 값 (`server.js:1584`):

| 파라미터 | 의미 |
|---|---|
| `andTerms` / `orTerms` / `notTerms` | 포함(전부) / 포함(하나라도) / 제외 키워드 |
| `pageNo`, `perPage` | 페이지 번호, 페이지당 행수. `all` 이면 99999, 그 외 1~500 클램프 |
| `fromDate`, `toDate` | `YYYYMMDD` |
| `insttNm` | 수요기관명 |
| `corpNm` | 낙찰업체명 — **UI 에서는 도달하지 못하는 사문 파라미터다**(§8 참고). 이식본도 같다: 못 이식한 것은 이 파라미터가 아니라 '낙찰자 조회' 모드와 company-history 패널 쪽이다 |
| `sortKey`, `sortDir` | 정렬 |
| `searchField` | `item` 이면 품목명(`dtilPrdctClsfcNoNm`) 단독 조회 |
| `bidType` | 전체 / 물품 / 용역 / 공사 |

`andTerms`·`orTerms`·`insttNm`·`corpNm` 이 **모두 비면 외부 API 를 부르지 않고 즉시 빈
목록을 반환한다**(`server.js:1589`). 프론트도 "포함할 키워드를 하나 이상 입력하고 Enter
또는 검색 버튼을 누르세요"로 막는다. 뒤집으면 **키워드 없이 기관명 단독 조회는 허용**된다.

### 3.2 상류 API 팬아웃

물품·용역·공사 3개 오퍼레이션(`getScsbidListSttus{Thng|Servc|Cnstwk}PPSSrch`)을 동시에
호출해 합친다. 외자 오퍼레이션은 쓰지 않는다.

검색어가 있으면 **한 검색어를 세 갈래로 각각 질의한다** (`server.js:1615-1620`):

1. 공고명 `bidNtceNm`
2. 품목분류명 `dtilPrdctClsfcNoNm`
3. 수요기관명 `dminsttNm` — 단 `insttNm` 이 지정됐거나 품목 모드면 생략

그 뒤 `bidNtceNo` 로 중복 제거하고, AND/OR/NOT → 기관명 → 업체명 → 업무구분 순으로
서버가 다시 거른다.

날짜는 **최대 31일 창**으로 쪼개 동시성 4로 병렬 호출하고, 범위 오류·타임아웃이면 구간을
반씩 쪼개 최대 5단계까지 재귀 재시도한다.

### 3.3 구분(물품/용역/공사) 필터

전체·물품·용역·공사 4버튼. 이것은 화면 필터가 아니라 **호출할 엔드포인트 자체를 좁힌다**
(`endpointsForBidType`, `server.js:1602`). 응답도 `filterByBidType` 으로 다시 거른다.
선택값은 `localStorage` 에 저장되고 상태바에 `| 구분: 물품` 으로 표시된다.

### 3.4 기간

`from-date` / `to-date` 두 입력과 **오늘 · 1주일 · 2주일 · 1달** 퀵버튼. 퀵버튼은 누르는
즉시 재조회한다. 기본값은 최근 30일이고, 낙찰자·담당자 조회 모드로 들어가면 90일로
자동 확장된다.

### 3.5 캐시

2단이다.

- **검색 캐시** 2시간 — 필터까지 끝난 결과 배열을 통째로 저장. 히트하면 외부 API 를 한
  번도 부르지 않고 정렬·페이징만 다시 한다. 응답에 `_cached: true` 가 실린다.
- **개별 호출 캐시** 6시간 — 그 아래 개별 나라장터 호출 단위. 동일 키 in-flight 프로미스를
  공유한다.

둘 다 메모리 `Map` 이라 프로세스가 재기동하면 사라진다.

### 3.6 페이징

무한 스크롤이 아니라 **10개 단위 블록 번호 페이징**이다. 페이지당 행수는 20 · 50 · 100 ·
전체. `전체`를 고르면 `perPage='all'` → 서버가 `numOfRows=99999` 로 1페이지에 몰아 받는다.

## 4. 결과 표시

### 4.1 컬럼 11개

`public/app.js:60` 의 `TABS['bid-result'].columns` 순서 그대로.

| # | 라벨 | 키 | 포맷 |
|---|---|---|---|
| 1 | 구분 | `_type` | 색 알약 배지 (물품 파랑 / 용역 보라 / 공사 초록) |
| 2 | 공고번호 | `bidNtceNo` | — |
| 3 | 공고명 | `bidNtceNm` | 포맷터 없음(클릭 불가) |
| 4 | 수요기관 | `dminsttNm` | — |
| 5 | 낙찰업체 | `bidwinnrNm` | — |
| 6 | 낙찰금액 | `sucsfbidAmt` | 천단위 콤마 + `원`, 강조 |
| 7 | 낙찰률 | `sucsfbidRate` | 알약 `%` |
| 8 | 참여업체수 | `prtcptCnum` | — |
| 9 | 개찰일시 | `rlOpengDt` | `YYYY-MM-DD HH:MM` |
| 10 | 낙찰확정일 | `fnlSucsfDate` | 날짜 |
| 11 | 공고보기 | `bidNtceNo` | 회색 `공고보기 →` 버튼 |

빈 값은 회색 `-`. 입찰 공고 탭에 있는 수주기회 점수 · D-DAY · 출처 배지 컬럼은 이 탭에 없다.

> **낙찰률은 서버 계산값이 아니다.** `sucsfbidRate` 는 조달청이 준 값을 그대로 올린다.
> open 의 `server.js` 전체에 이 필드에 대한 대입·산술이 한 줄도 없다. `_type` 만은 API 값이
> 아니라 호출한 URL 이름(`Cnstwk`/`Servc`/기타)으로 판정한 값이다.

### 4.2 정렬

11개 컬럼 **전부** 헤더 클릭 정렬. 같은 컬럼 재클릭 시 `asc ↔ desc` 토글, 다른 컬럼은
`asc` 로 시작. 정렬하면 1페이지로 돌아가 서버에 `sortKey`/`sortDir` 를 실어 재조회한다.
서버는 값이 날짜꼴이면 날짜, 숫자꼴이면 숫자, 아니면 한국어 로케일로 비교한다.

### 4.3 상태바 · 로딩

조회가 끝나면 `총 N건 | YYYY-MM-DD ~ YYYY-MM-DD | p / P 페이지` 를 표시하고, 구분 필터가
걸려 있으면 `| 구분: 물품` 이 붙는다. 로딩 중에는 5행 스켈레톤, 오류면 빨간 상태바,
API 키 미승인 상태면 안내 화면으로 대체된다.

### 4.4 화면 히스토리 · 세션 복원

탭 전환 · 검색모드 변경 · 퀵기간 · 구분 필터 · 정렬 · 페이지 이동 · 크로스탭 · 프리셋 적용이
모두 스냅샷으로 기록돼 `← 뒤로 / 앞으로 →` 로 되돌아간다(각 최대 10단계).
탭 · 검색모드 · 키워드 · 기간 · 구분은 `localStorage`(`g2b_ui_state`)에 저장돼 재방문 시
복원되고, 조건이 있으면 자동 검색까지 실행된다. `perPage` 와 `sortKey` 는 저장되지 않아
새로고침하면 20건 · 기본 정렬로 돌아간다.

## 5. 상세 드로어

행 마지막 칸의 `공고보기 →` 는 **탭 이동이 아니라** 같은 행 데이터를 우측 드로어에 띄운다.

드로어 구성:

1. **메타 그리드** — 값이 있는 항목만 남긴다. 낙찰정보 레코드에는 추정가격·마감일시·담당자
   같은 필드가 없어 실제로는 공고번호·수요기관·공고명 정도만 찬다.
2. **AI 분석** — 드로어가 열리면 자동으로 `POST /api/bid-summary` 를 부른다. 출처 라벨
   (`📄 첨부파일 자동 분석` / `📋 공고 원문 자동 분석` / `⚠️ 기본정보 기반`)과 함께 렌더되고
   실패하면 `다시 시도` 버튼이 뜬다. 낙찰정보 행은 첨부가 없어 대개 "기본정보로만 분석"
   경로를 탄다. main 은 Groq `llama-3.3-70b-versatile` 을 쓴다.
3. **개찰 경쟁 현황** — 아래 §6.

Esc · 오버레이 · × 로 닫힌다.

## 6. 개찰 경쟁 현황

드로어 하단의 `[조회]` 버튼을 눌러야 실행된다(자동 아님). `POST /api/bid-opening-results` 로
그 공고의 참가업체 전원을 불러 표를 그린다.

| 열 | 내용 |
|---|---|
| 순위 | 개찰 순위 |
| 업체명 | 참가업체 |
| 투찰금액 | 금액 |
| 투찰율 | 소수 3자리 |
| 낙찰여부 | 낙찰사 행은 굵게 + 강조 배경 + `✅ 낙찰` |

아래에 `총 N개사 참여`. 데이터가 없으면 `개찰결과 미공개 또는 아직 집계 전입니다`.

서버는 낙찰정보와 **다른 서비스**인 개찰결과정보서비스(`OpengResultInfoService`)를
`inqryDiv=2` · 공고번호 단건으로 호출하고, 실패해도 예외를 던지지 않고 빈 배열을 돌려준다.

## 7. 분석 기능

### 7.1 들러리 매트릭스 (이 탭 전용)

결과가 1건 이상이고 현재 탭이 입찰 결과일 때만 보라색 `들러리 매트릭스` 버튼이 켜진다
(`public/app.js:1195`). 누르면 **현재 결과 최대 20건**의 개찰결과를 병렬로 모아
(`POST /api/collusion-analysis`) 모달을 띄운다.

`buildCollusionMatrix` 는 `server.js:3009` 에 **인라인으로 구현**돼 있다. LLM 없는 순수
그래프 연산이다.

**① 페어별 공동출현 분석**

| 열 | 내용 |
|---|---|
| 업체 A / 업체 B | 함께 나타난 두 업체 |
| 공동출현 | 같은 공고에 함께 등장한 횟수 `total` |
| 낙찰분포 | `N승 / M승` |
| 교대율 | `1 - |aWins - bWins| / total` — 공동출현 2회 이상일 때만 계산 |
| 위험도 | 🔴 `≥3` / 🟡 `≥1.5` / ⚪ |

의심점수 `suspicionScore = total × 교대율` (소수 첫째 자리). 위험도 임계값 3.0 / 1.5 는
**프론트에만** 있다.

**② 업체별 투찰 패턴** — 낙찰 · 2위 · 출현 횟수, 평균 투찰율, 투찰율 추이와
`⚠️ 단조증가` 플래그(투찰율 `bidprcRt` 표본 3회 이상 **비감소**).

**③ 공고별 개찰 결과** — 1 · 2위 표.

상단에 `분석 N건 중 개찰결과 확인 M건` 고지가 붙는다.

### 7.2 낙찰자(업체) 프로파일

검색 방식에서 `낙찰자 조회` 를 고르면 업체명(+선택 사업자번호) 입력 행이 열리고 기간이
90일로 확장되며, 검색 시 탭이 입찰 결과로 강제 전환된다. **단 화면은 표가 아니라 업체
프로파일 패널로 대체되고 호출도 `POST /api/company-history` 로 빠진다.**

- 낙찰 / 참여 건수, 낙찰률, 평균 투찰률 KPI
- 투찰률 성향 SVG 꺾은선 (낙찰 초록점 · 미낙찰 파랑점, 툴팁에 날짜 · 공고명 · 투찰률 · 순위)
- `낙찰 이력` / `참여 이력` 두 서브탭 표

화면에 `3개월 개찰결과 기준 · 나라장터 API 1페이지(최대 500건×3업종) 범위 내 조회`라는
표본 한계가 고지된다.

### 7.3 담당자 조회

기관명으로 담당자(이름 · 전화 · 이메일)별 담당 공고 목록을 공고 수 내림차순으로 보여준다.
검색모드 UI 상 `낙찰자 조회` 바로 옆에 놓여 경쟁정보 한 묶음처럼 보이지만, 실제로는
낙찰정보가 아니라 **입찰공고서비스**(`BidPublicInfoService`)를 조회하므로 입찰결과
데이터와 직접 연결은 없다.

## 8. 내보내기

결과가 있으면 `엑셀 다운로드` 버튼이 켜진다. 누르면 **현재 검색 조건 그대로 `pageNo=0`
(전량)으로 재조회**해 SheetJS 로 `.xlsx` 를 만든다.

- 헤더는 화면 컬럼 11개와 동일
- 낙찰금액은 숫자, 낙찰률은 `값%`, 날짜는 화면 표기 문자열
- 열 너비 프리셋: 공고명 42 · 낙찰업체 20 · 공고번호 18 · 수요기관 22 · 구분 6 · 기본 14
- 시트명 `입찰 결과`, 파일명 `G2B_입찰 결과_<키워드>_<날짜>.xlsx`

버튼 id 는 `btn-csv` 지만 CSV 가 아니다.

## 9. 이식할 때 따라 옮기지 말아야 할 것 (open 의 알려진 결함)

이 절은 "open 과 똑같이 만든다"가 곧 "open 의 버그까지 옮긴다"가 되지 않도록 남긴다.

1. **검색 캐시 키가 `corpNm`·`bidType` 을 버린다.** 호출부(`server.js:1591`)는 넘기는데
   함수 본문(`server.js:52`)이 구조분해에서 뺀다. 저장값은 이미 타입 필터가 적용된
   배열이라, **2시간 안에 물품 → 공사로 바꾸면 0건이 나온다.** 이식할 때는 캐시 키에
   모든 조건을 넣어야 한다.
2. **AND 키워드는 첫 항만 상류 API 에 나간다** (`server.js:1615`). 나머지 AND/NOT 은 이미
   잘린 표본 위에서 로컬 필터로만 걸린다. AND 검색일수록 유실이 커진다.
3. **수집 상한 100건** (`RESULT_ROWS`). open 의 `dev`·`fetch` 브랜치는 "그 제한은 실측 결과
   존재하지 않았다"며 999 로 올렸고 "상향 전에는 한 달 6,857건 중 100건만 수집해 98% 유실"
   이라는 근거를 남겼는데, `main` 에는 틀린 주석과 100 이 그대로 있다.
4. **그레인 손실** — `bidNtceNo` 만으로 중복 제거한다(`server.js:1629`). 이 API 의 자연
   그레인은 `(공고번호, 차수, 입찰분류, 재입찰차수)` 4열이라 한 공고의 분류별 · 재입찰차수별
   낙찰 행이 첫 1건만 남고 버려진다.
5. **드로어의 개찰 결과가 공고를 바꿔도 초기화되지 않는다.** A 공고에서 조회한 뒤 B 공고를
   열면 A 의 참가자 표가 B 의 결과처럼 남는다.
6. **BM25 재랭킹은 사실상 죽은 코드다.** 서버는 `sortKey` 가 없을 때만 BM25 를 타는데
   프론트가 모든 경로에서 `sortKey='rlOpengDt'` 를 세팅한다.

   > **2026-08-29 — 이식본에서 닫았다.** 이 결함은 그대로 따라와 있었다.
   > 지금은 URL 에 정렬이 명시되지 않았고 키워드 조건이 있을 때만 `sortKey` 를 생략해
   > 서버가 관련도로 답하게 하고, 상태 줄에 '관련도순 정렬'을 적는다
   > (`src/routes/NoticeTableScreen.tsx` 의 `relevanceSort`). 사용자가 머리글을 눌러 고른
   > 정렬은 그대로 우선한다.
7. **문서상 실측은 FAIL 이다.** open 의 `docs_archive/FEATURE_MAP.md:78-79` 가 개찰 참여업체
   조회를 FAIL(`participants: []`), 들러리 분석을 FAIL(`pairs`·`companies` 0)로 기록했다.
   원인 함수 `fetchBidOpeningResults` 는 어느 브랜치에서도 수정되지 않았다. **코드가 있다는
   것과 실제로 값이 온다는 것은 다르다** — 이식 후 반드시 실데이터로 확인해야 한다.

   > **2026-08-29 — 원인은 확인됐고 해소됐다.** 위 FAIL 의 원인은 구현이 아니라 **오퍼레이션
   > 폐기**였다. `ao/OpengResultInfoService` 가 `NO_OPENAPI_SERVICE_ERROR`(사유코드 12)를
   > 돌려주고 있었고, 백엔드가 `as/ScsbidInfoService/getOpengResultListInfoOpengCompt` 로
   > 갈아 끼우면서(`G2bEndpoints.java:33-36` 이 스스로 그 사실을 지목한다) 응답 정규화까지
   > 화면 계약에 맞췄다. 프론트는 고칠 것이 없었다.
   >
   > **다만 위 경고문 자체는 여전히 유효하다** — 코드로 증명되는 것은 '살아 있는 오퍼레이션으로
   > 교체됐다'까지이고, 상류가 실제로 값을 주는지는 소스만으로 알 수 없다. 라이브 검증은
   > 아직 하지 않았다.
   >
   > 이 항목이 오래 스테일로 남아 있던 대가가 실제로 있었다: 개찰 참여업체 정렬이 실격 업체를
   > 낙찰 1위 위로 올리는 결함이 "원래 비는 게 정상"이라는 서술 뒤에 가려져 있었다
   > (`src/features/notices/rows.ts` 의 `rankOf`).

## 10. open 브랜치 간 차이 (참고)

입찰 결과 탭 자체는 `main`·`dev`·`fetch` 가 사실상 동일하고, 갈리는 곳은 넷뿐이다.

| 항목 | main (배포판) | dev · fetch |
|---|---|---|
| 수집 상한 `RESULT_ROWS` | 100 | 999 |
| 빈 쿼리 가드 | 있음 | fetch 는 제거(기간만으로 브라우징 가능, 기본 7일) |
| 검색 캐시 키 | `corpNm`·`bidType` 누락 | `lib/notice-search.js` 로 전 파라미터 해싱 |
| AI 백엔드 | Groq `llama-3.3-70b-versatile` | LM Studio / OpenAI 호환 |

`dev`·`fetch` 가 추가한 `POST /api/deal-analysis`(낙찰률 중앙값 시가 · 투찰 시뮬)와
PostgreSQL 낙찰 창고(`dwt_bid_result`)는 입찰 결과 탭이 아니라 **신설 AI 수주 데스크
탭**에서 쓴다. 창고가 있는 `fetch` 조차 `/api/bid-result` 는 여전히 실시간 API 를 친다.

또 하나: **입찰 결과에는 국방전자조달(D2B)이 합류하지 않는다.** D2B 는 입찰 *공고*
라우트에서만 병합되고 낙찰 오퍼레이션 자체가 코드에 없다. 결과적으로 입찰 결과 행의
출처는 언제나 `나라장터` 하나다.
