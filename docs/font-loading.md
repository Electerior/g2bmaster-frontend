# 폰트 로딩 결정 기록 — Pretendard dynamic-subset

작성: 2026-08-27 · 대상: `index.html` 폰트 블록, `src/styles/tokens.css` 의 `--font-sans`

성능 감사가 `index.html` 의 Pretendard 로드를 **Medium — render-blocking third-party font
CSS** 로 올리고 두 가지를 제안했다: (1) 서브셋 자체 호스팅, (2) `media="print" onload` 비블로킹.
둘 다 실측해 보고 **쓰지 않기로 했다.** 대신 조각 두 개를 `preload` 한다. 아래가 근거다.

> 감사 자체가 *"No LCP, INP or CLS number in this report is measured"* 라고 밝히고 있다.
> 여기 적은 숫자는 전부 네트워크에서 직접 잰 것(파일 크기·헤더)이고, LCP/CLS 는 여전히
> 측정되지 않았다. 그래서 큰 변경을 넣지 않았다.

## 실측치

`https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css`

| 항목 | 값 |
|---|---|
| CSS 원본 / 전송(br) | 53,513 B / **12,493 B** |
| `@font-face` 규칙 수 | **92** (전부 `font-display: swap`) |
| woff2 조각 수 | **92** |
| woff2 합계 | **2,957,724 B (2.82 MB)** |
| 조각 하나 평균 / 최소 / 최대 | 32,149 B / 8,252 B / 43,920 B |
| CSS·woff2 캐시 | `public, max-age=31536000, immutable`, `access-control-allow-origin: *` |

이 저장소가 실제로 쓰는 양(코드 안의 한글·한자를 전부 unicode-range 에 대입해 계산):

| 범위 | 조각 수 | 합계 |
|---|---|---|
| 첫 화면(제목 + 상단 내비 수준) | 8 / 92 | **206,328 B (202 KB)** |
| 코드베이스에 등장하는 모든 글자 | 36 / 92 | 1,060,576 B (1.04 MB) |

비교 대상: 통짜 가변 폰트 `dist/web/variable/woff2/PretendardVariable.woff2` = **2,057,688 B (1.96 MB)**.

## 선택지 1 — 자체 호스팅: 안 한다

- **조각 전부를 담는 안.** 92개 파일 2.82 MB 를 저장소에 넣어야 한다. 크기도 크기지만
  `public/` 은 지금 다른 브랜치가 쥐고 있어 충돌한다. 얻는 것은 이미 preconnect 로 데워 둔
  연결 하나를 아끼는 것뿐이다.
- **통짜 파일 하나로 바꾸는 안.** 파일은 하나지만 **2.06 MB 를 전부 받아야 첫 글자가 뜬다.**
  지금은 첫 화면이 202 KB 만 받는다. 10배 느려지는 거래다. dynamic-subset 을 고른 원래
  판단이 옳았다는 뜻이기도 하다.
- **필요한 조각만 골라 담는 안.** 36개 1.04 MB. 게다가 이 앱은 나라장터 공고 제목을 그대로
  표시한다 — 어떤 한자·희귀 음절이 나올지 빌드 시점에 알 수 없다. 조각을 고정하면 화면에
  구멍(폴백 글꼴로 튀는 글자)이 생긴다. **92개 규칙을 전부 유지해야 하는 이유가 이것이다.**

jsdelivr 쪽 조건도 자체 호스팅 압력을 낮춘다: Cloudflare 엣지, `immutable` 1년 캐시,
CORS 전면 허용, 전송 12.5 KB.

**언제 자체 호스팅으로 넘어가야 하나** — 아래 중 하나라도 참이 되면 다시 검토할 것:

1. jsdelivr 접근이 실제로 막히는 사용자군이 확인될 때(사내망 화이트리스트, 특정 국가 차단).
   증상은 "글꼴만 다르게 보인다"라 신고가 잘 안 들어온다 — 문의가 오면 이 항목을 의심해라.
2. 프리렌더가 들어와 본문이 HTML 로 나가기 시작할 때. 그때는 폰트가 진짜 크리티컬 패스에
   올라오므로 첫 화면 조각(현재 90·91)을 자체 호스팅해 왕복 하나를 더 줄일 값어치가 생긴다.
   **전부가 아니라 그 두 조각만** 옮기면 되고, 나머지는 CDN 에 남긴다.
3. CSP 를 `font-src 'self'` 로 좁혀야 하는 요구가 생길 때.
4. 실측 LCP 에서 폰트 CSS 가 실제로 상위 항목으로 잡힐 때. **지금은 아니다** — 감사 자신이
   High 로 올린 608 KB 단일 JS 청크가 지배 항목이고, 본문이 비어 있어 그 JS 가 실행되기
   전에는 아무것도 그려지지 않는다.

## 선택지 2 — `media="print" onload`: 안 한다

이유 셋. 앞의 둘이 결정적이다.

1. **FOUT 는 지금도 일어난다.** 92개 규칙이 **전부 `font-display: swap`** 이다. 블로킹
   `<link>` 는 교체를 막아 주지 않는다. 즉 비블로킹으로 바꿔서 "새로 생기는" FOUT 은 없다 —
   대신 **교체 시점이 밀린다.**
2. **밀린 교체가 CLS 를 만든다.** 크롬은 `media="print"` 리소스를 낮은 우선순위로 내린다.
   CSS 가 늦게 오면 `@font-face` 발견도 늦고, 폰트가 첫 콘텐츠 페인트 **뒤에** 교체된다.
   지금은 CSS 가 먼저 도착해 있으므로 교체가 페인트 직후 한 번에 정리될 여지가 있다.
   12.5 KB 병렬 요청 하나를 아끼려고 감사가 지적 대상으로 올려 둔 CLS 를 악화시키는 거래다.
3. **인라인 `onload` 는 CSP 비용이 있다.** nginx 브랜치가 `Content-Security-Policy-Report-Only`
   를 넣는 중이다. 인라인 핸들러를 쓰면 폰트 하나 때문에 `script-src 'unsafe-inline'` 을
   열어야 한다. 그리고 `<noscript>` 폴백을 따로 둬야 하는데, 지금 구조는 평범한 블로킹
   `<link>` 라 **JS 없이 오는 크롤러·사용자에게도 폰트가 그대로 간다** — 폴백이 애초에 필요 없다.

## 실제로 한 것 — 첫 화면 조각 2개 preload

진짜 병목은 블로킹 여부가 아니었다. `unicode-range` 서브셋은 **화면에 그 글자가 실제로
그려져야** 조각을 받는다. 이 앱은 `<body>` 가 비어 있고 15개 화면이 정적 import 라
608 KB JS 가 전부 실행된 뒤에야 첫 글자가 그려진다 — 즉 **폰트는 CSS 가 아니라 JS 를 기다린다.**
교체가 첫 페인트 뒤에 오는 것이 구조적으로 보장돼 있었다.

그래서 요청 시점만 앞으로 당겼다:

| 조각 | 크기 | 덮는 범위 |
|---|---|---|
| `subset.91` | 37,996 B | 라틴·숫자·문장부호 전부 + 최빈 한글 12자(가 고 기 다 로 리 사 스 시 이 인 지 하) |
| `subset.90` | 20,852 B | 그다음 한글 43자(간 개 거 게 경 공 과 관 구 그 나 내 는 니 대 도 …) |
| 합계 | **58,848 B (57.5 KB)** | |

어느 화면을 열어도 헤더·내비·날짜·금액이 이 둘에 들어가므로 헛되이 받는 경우가 없다.
나머지 90개 조각은 그대로 필요할 때만 받는다.

- **효과**: 폰트 다운로드가 JS 다운로드와 겹친다. JS 가 다 돌 무렵엔 대개 폰트가 이미 와 있어
  교체 자체가 일어나지 않는다 — 위 2번에서 걱정한 CLS 를 근본에서 줄인다.
- **비용**: 57.5 KB 를 JS(전송 196 KB) 앞에 세운다. 한국 4G 기준 수십 ms 단위로 **LCP 를
  늦출 수 있다.** 측정되지 않은 거래이므로, 실측이 불리하게 나오면 `index.html` 의 preload
  두 줄만 지우면 원상복구다.
- **주의**: JS 가 아주 느린 회선에서 3초 넘게 걸리면 크롬이 "preloaded but not used" 경고를
  콘솔에 남길 수 있다. 기능 문제는 아니다. 608 KB 청크를 쪼개면(감사의 High 항목) 같이 사라진다.
- **부수 비용**: `index.html` 의 설명 주석 때문에 문서가 커졌다 — `dist/index.html`
  7,425 B → 10,122 B(gzip 2,815 → 3,969, **+1,154 B**). HTML 은 `no-cache` 라 첫 방문마다
  전송되지만 재방문은 304 로 끝난다. 이 저장소는 `<head>` 규칙을 산문으로 남기는 쪽을 택해
  왔고(SEO 블록도 같다), 그 값이 이 정도라는 것까지 적어 둔다.

## 메트릭 보정(`size-adjust`)은 하지 않았다

교체 순간의 흔들림을 줄이는 표준 처방이지만 여기서는 값어치가 없다고 판단했다:

- 한글 음절은 Pretendard·Apple SD Gothic Neo·맑은 고딕·Noto Sans KR 어디서나 **전각(1 em)**
  이라 교체해도 글자폭이 사실상 그대로다. 폭이 바뀌는 건 라틴·숫자뿐이다.
- 줄상자 높이는 `global.css` 의 `line-height: 1.5`(단위 없는 배수)가 고정한다. 폰트의
  ascent/descent 가 달라져도 블록 높이가 따라 움직이지 않는다. (저장소 전체에서 `line-height`
  선언은 이 한 줄뿐이다.)
- 폴백은 macOS·윈도우·안드로이드에서 **서로 다른 글꼴**로 잡힌다. 하나의 `size-adjust` 값이
  셋을 동시에 맞출 수 없고, 틀린 값을 넣으면 웹폰트가 못 올 때 글자 크기가 어긋난 채로
  남는다 — 지금보다 나쁘다. 제대로 하려면 세 플랫폼의 실제 폰트 메트릭을 재야 한다.

남는 위험은 라틴·숫자 폭 변화로 긴 공고 제목의 줄바꿈 위치가 달라지는 경우다. 이건 preload
가 교체 자체를 없애는 쪽으로 다룬다.

## 다음 사람에게

- **버전을 올릴 때는 URL 세 개를 함께 올려라** (stylesheet 1 + preload 2). 한쪽만 올리면
  아무도 안 쓰는 파일을 조용히 받아 온다. `src/test/indexHtmlFont.test.ts` 가 막는다.
- 조각 번호(90·91)는 Pretendard 버전에 묶여 있다. 버전을 올렸으면 새 CSS 를 받아
  `unicode-range` 를 다시 확인해라 — 번호가 바뀌면 preload 가 엉뚱한 조각을 받는다.
- **CSP 담당께**: 이 블록에 인라인 핸들러는 없다. 필요한 것은 `style-src` 와 `font-src` 의
  `https://cdn.jsdelivr.net` 뿐이다.
- 폰트를 더 손대기 전에 감사의 High 두 항목(코드 스플리팅, 프리렌더)을 먼저 봐라. 폰트는
  그 뒤에 있는 12.5 KB 짜리 병렬 요청이다.
